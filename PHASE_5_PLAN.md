# Phase 5 — ISO 8583, Acquirer Host, Scheme Simulator (Plan)

**Status:** Proposed for review · **Predecessor:** Phase 4 (`PHASE_4_DONE.md`).

> This is the heart of the technical learning. Do not skip the realism.
> — PROJECT_BRIEF.md §3 Phase 5

Phase 5 replaces the always-approve stub acquirer with **a real ISO 8583
exchange**. After this phase, a card payment in the platform travels through
genuine card-network-style message wire formats — the only thing pretending
is the scheme itself.

---

## Goal

A PaymentIntent confirmation walks this path:

```
api → acquirer-host (TCP) → scheme-simulator (TCP)
                                      │
                                      ▼ BIN → simulated issuer
                                  apply decline rules / approve
                                      │
                                      ▼
                              0110 auth response with DE 39 RC
                                      │
                                      ▼
api ← acquirer-host ← scheme-simulator
   ↓
post journal entry / mark PaymentIntent succeeded / failed
```

Plus end-of-day clearing files (Visa Base II-like + Mastercard IPM-like)
generated by the scheme-simulator from the day's transactions.

---

## Pieces

### A. `packages/iso8583` — the codec, written from scratch
- ISO 8583:1987, ASCII variant per ADR (Phase 0 Q24)
- 4-byte ASCII length-prefix framing (Phase 0 simulator already has the reader)
- MTI parser/builder
- Primary + secondary bitmap (DE 1) encoding
- Codec for the brief's listed DEs:
  - **Numeric:** 2, 3, 4, 7, 11, 12, 13, 14, 22, 37, 38, 39, 41, 42, 49, 90, 102, 103
  - **LLVAR:** 32, 35
  - **LLLVAR:** 48 (incl. .43 sub-field), 55, 62, 63, 64
- Property-based tests via fast-check: `decode(encode(x)) === x` for every
  field type. Round-trip every supported MTI.

### B. `apps/acquirer-host` — the 8583 client
- Persistent TCP connection to the scheme-simulator (Phase 0 already opens it).
- Connection manager: reconnect with backoff, heartbeat (0800 network
  management messages), STAN allocator (6-digit, recycled).
- Authorization flow:
  - Receive request from api over service-auth HTTP (`/internal/v1/authorize`)
  - Call vault.detokenize(token, merchant, reason='authorization')
  - Build 0100 message with PAN + amount + currency + STAN + RRN + DE 48.43
    (3DS data from `paycore.three_ds_sessions`)
  - Send framed message, await response (15s timeout)
  - On timeout: send 0400 auto-reversal
  - Return parsed response to api
- Reversal flow (0400/0420 advice) on capture/refund/cancel

### C. `apps/scheme-simulator` — the issuer
- Receive 0100 authorization request
- Lookup BIN → which simulated issuer
- Apply per-BIN decline rules (configurable JSON file):
  - Approve (RC 00)
  - Insufficient funds (RC 51)
  - Do not honor (RC 05)
  - Expired card (RC 54)
  - Stolen card (RC 43)
  - Soft decline triggering step-up (RC 1A — usually triggers 3DS in real life)
- Respond with 0110
- Log everything for the audit trail
- End-of-day job: emit clearing files

### D. `apps/api` integration
- Replace the stub acquirer in `confirmPaymentIntent` + `completeThreeDs` with
  a call to acquirer-host over HTTP service-auth.
- The response code maps to PspError decline codes:
  - 00 → success
  - 51 → `card_declined` decline_code=`insufficient_funds`
  - 05 → `card_declined` decline_code=`do_not_honor`
  - etc.

### E. Clearing files
- `paycore.scheme_clearing_records` table to track outbound clearing
- Visa Base II-like CSV emitted per-day per-currency
- Mastercard IPM-like CSV (similar format, slightly different DE handling)
- Filename convention: `<scheme>_<currency>_<YYYYMMDD>.csv`
- Written to `data-exports/` storage bucket / dir

### F. Reversal flows
- Capture from `requires_capture` triggers 0200 financial
- Refund creates a 0420 reversal advice
- Cancel from `requires_capture` triggers 0400 reversal of the original auth

## Schema

Migration `0014_acquirer_journal.sql`:

```sql
create table paycore.acquirer_messages (
  id              text primary key,             -- am_<ulid>
  payment_intent_id text not null references paycore.payment_intents(id),
  scheme          text not null,
  direction       text not null check (direction in ('outbound', 'inbound')),
  mti             char(4) not null,
  stan            char(6) not null,
  rrn             char(12) not null,
  body_hex        text not null,                 -- the raw 8583 message, redacted PAN
  response_code   char(2),                       -- for 0110/0210/0410
  occurred_at     timestamptz not null default now()
);
create index acquirer_messages_pi_idx on paycore.acquirer_messages (payment_intent_id);
create unique index acquirer_messages_stan_idx on paycore.acquirer_messages (stan, occurred_at);
```

Migration `0015_scheme_clearing.sql`:

```sql
create table paycore.scheme_clearing_records (
  id              text primary key,
  payment_intent_id text not null,
  scheme          text not null,
  currency        char(3) not null,
  amount          bigint not null,
  rrn             char(12) not null,
  stan            char(6) not null,
  clearing_file_id text,
  occurred_at     timestamptz not null default now()
);

create table paycore.clearing_files (
  id              text primary key,
  scheme          text not null,
  currency        char(3) not null,
  file_date       date not null,
  record_count    int not null,
  total_amount    bigint not null,
  path            text not null,             -- on-disk path for Phase 5; storage URL Phase 8
  created_at      timestamptz not null default now()
);
```

## Tests

- **Codec unit:** Decode every fixture MTI from the brief. Round-trip every
  field via property-based test.
- **Acquirer-host unit:** Build a 0100 from a synthetic `AuthRequest` → encode
  → frame → assert bytes.
- **Scheme-simulator unit:** Decode a frame → apply BIN rules → encode 0110 →
  assert RC.
- **End-to-end (DB+TCP-gated):** Spin up acquirer-host + scheme-simulator in
  process; create PaymentIntent → confirm → assert journal entry, response
  code, message-pair audit, all correct.
- **Chaos mode:** Random drop / delay / duplicate response from simulator;
  assert convergence + correct reversals.
- **Clearing files:** After N transactions, run EOD job → assert file rows +
  totals + record count.

## Open questions for you

1. **Codec encoding convention**: pure ASCII (BCD-as-ASCII for numeric fields)
   is simplest; closer to real Visa Base I + Mastercard MIP is to use BCD-on-wire
   for numeric LLVARs (DE 35, 55) — saves bytes, harder to debug. My recommendation:
   **ASCII everywhere** for Phase 5 (matches brief Q24 + much easier to debug).
2. **STAN exhaustion behavior**: 6-digit STAN = 1M values; we recycle after
   100k auths. My recommendation: **per-day reset** since real schemes do this.
3. **0420 reversal advice retries**: per ISO spec, reversal must keep retrying
   until ACKed. My recommendation: **persist in `paycore.acquirer_messages`
   with `delivered_at` null until ACKed**; BullMQ retries with exponential
   backoff like webhooks.
4. **Clearing file format**: do you want literal Visa Base II / Mastercard IPM
   format (lots of fixed-width fields, real-world headaches), or "close-enough"
   CSV with the right fields? My recommendation: **close-enough CSV** for
   Phase 5; literal format is doable in Phase 6 if we plan to integrate with
   a real reconciliation tool.

Answer those and I execute Phase 5.
